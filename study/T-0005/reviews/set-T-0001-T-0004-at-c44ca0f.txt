## Findings, most important first

**1. The set checks whether the LSP can be made to work, never whether it's worth it (all four tasks).**
- The repo has 11 Markdown files, about 520 lines in all; the longest is 116 lines.
- No task points to an actual problem, such as agents reading too much Markdown.
- The plan is still large: a plugin, a relay (preferably in Rust), a new pinned dependency, two ADRs and a docs page.
- `context-engineering/semantic-context-loading.md` says LSP pays off on large codebases, names grep as the thing to beat, and says that when one grep finds the target, "the LSP round-trip rarely pays for itself."
- `patterns/agent-design/minimum-sufficient-control-ladder.md` and `patterns/anti-patterns/cargo-cult-agent-setup.md` both say to add machinery only for a named, observed failure.
- Your decision to pursue rumdl stands. The gap is that the go/no-go never weighs the benefit.
- Suggestion: add one criterion to T-0004 or T-0002. Answer a fixed set of navigation questions (outline, a section, backlinks) once with the LSP and once with Grep/Read, and record tool calls and tokens for each.

**2. T-0004's "go" has no stated rule, and it doesn't match what T-0002 requires.**
- T-0002 passes only if all nine change routes stay fresh in one session.
- T-0004 lets whoever built the relay decide "go" from the results.
- T-0004 also lets changes you make on the host be recorded as "untested", and T-0002 has no host route at all. So T-0004 can say "go", T-0002 can then fail, or the plugin can ship stale after host edits.
- `patterns/agent-design/sprint-contracts.md`: fix the pass bar before the work, or the evaluator rationalizes whatever was built.
- `verification/evidence-gated-lifecycle-control.md` (When this backfires): a gate with a loose rule passes a wrong result.
- Suggestion: define "go" in T-0004 as "T-0002's freshness criterion can be met with one mechanism", and decide now whether host edits must be fresh.

**3. Most of T-0002's criteria can't fail, so "if it can't meet these criteria, don't merge it" never kicks in.**
- Six criteria only say "raw output … is recorded", and an empty result satisfies them.
- Only the `documentSymbol` criterion and the freshness criterion are real pass/fail tests.
- `verification/evidence-gated-lifecycle-control.md`: the gate "faithfully admits whatever the test proves." The board README's own rule makes the same point: a test criterion should name the behavior it checks.
- Suggestion: you decide which operations must return results for "the plugin works", and the task says the other operations are record-only.

**4. The relay works around a Claude Code gap, but nothing says when to remove it (T-0002, T-0004).**
- It exists because Claude Code rejects rumdl's `client/registerCapability`.
- T-0002 asks for a production rebuild, preferably in Rust, with no end condition.
- `patterns/agent-design/temporary-compensatory-mechanisms.md`: record what the workaround covers for, what would make it unnecessary, and how to remove it. Its backfire section warns against building feature flags for this; a written note is enough.
- Suggestion: T-0002's ADR states the removal condition, e.g. "Claude Code accepts `workspace/didChangeWatchedFiles` registration". Weighing a Rust toolchain for a stopgap is your call.

**5. Your review covers only the first version of executable config (T-0002).**
- Later changes to `.lsp.json`, the relay, or the rumdl version arrive by `git pull` and run at every session start without a prompt.
- `patterns/anti-patterns/install-once-plugin-trust.md`: trust is granted once, but the code that runs is re-read on every update.
- `security/gate-agent-writes-to-executable-config.md` and `security/pre-trust-execution-surface.md` cover the same kind of file. Their backfire sections apply here (solo, sandboxed, in-repo), so the risk is moderate, and reviewing the diff is only worth about 50% recall.
- The approval criterion only asks the evidence to say *where* you approved.
- `code-review/agent-approval-authority.md`: an approval should be dismissed when new commits follow it. `patterns/anti-patterns/trusting-claimed-prior-approval.md`: a verifier shouldn't accept a stated approval it can't check.
- Suggestion: require an approval on the final plugin commit, shown by a command such as `gh pr view --json reviews`. Whether to also add a check that flags future changes to the plugin folder or rumdl version is your call (it's tooling).
